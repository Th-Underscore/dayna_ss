# alias / branch-query map (read-only investigation)

Repo: extensions/dayna_ss — DataSummarizer (agents/data_summarizer/). Read-only; no source modified.

## Task 1 — ALIAS LISTING (how aliases are instructed, parsed, rendered)

### 1.1 Format/prompt templates (schema-injected instructions)

The model is told how to fill alias fields in exactly two ways, both inside
`user_data/example/subjects_schema.json` (the live run schema is the same file shape):

1. Per-field type annotation. Only 4 definitions declare an `aliases` field, each typed:
   - `definitions/CharacterGroupStatus/fields/aliases` = `list[str]`
   - `definitions/CharacterRelationship/fields/aliases` = `list[str]`
   - `definitions/Group/fields/aliases` = `list[str]`
   - `definitions/StoryEvent/fields/aliases` = `list[str]`
   i.e. **`aliases: list[str]` — a bare string list with zero descriptive metadata.**

2. Per-field placeholder (the `defaults/<field>_placeholder` mechanism, consumed at
`utils/schema_parser.py:206-208` (-> JSONSchema `description`) and `:300-320` (-> example value).
These placeholders are the ONLY natural-language instructions a model ever receives about
alias-field contents. Verbatim, for every aliases placeholder in the schema:

   - `defaults/CharacterGroupStatus/defaults/aliases_placeholder` = "Alternative names or titles for the character within this specific status context (e.g., 'Leader', 'Hellion')."
   - `defaults/CharacterRelationship/defaults/aliases_placeholder` = "A list of nicknames or alternative terms for the related character in the context of this specific relationship (e.g., ...)"
   - `defaults/Group/defaults/aliases_placeholder` = "Alternative names or shorthand for the group."
   - `defaults/StoryEvent/defaults/aliases_placeholder` = "A list of alternate names or aliases for the story event."

**Critical gap — 2 of the 4 alias-bearing fields have NO placeholder at all:**
   - `definitions/CharacterGroupStatus/defaults/aliases_placeholder` — ABSENT from the schema (verified by full key scan of all defaults; only the 4 placeholders above exist).
   - `definitions/CharacterRelationship/defaults/aliases_placeholder` — ABSENT from the schema (verified by full key scan of all defaults; only the 4 placeholders above exist).
   The model therefore receives the bare type `list[str]` for these two and no prose contract whatsoever.

No other instruction channel exists: no `to_context`/`to_prompt` render flag, no worked
example file for aliases (only inline `example_json` auto-generated by `generate_example_json`
from the placeholder, which for the two placeholder-less fields is the empty/default value),
and no template line in any of the 34 summarizer prompt templates (gate_check / branch_query /
branch_update / update / new_entry_query) mentions an alias contract. Full grep of all 34
extracted templates (tests/_tmpl_extract/) shows the only alias mentions are incidental
enumerations inside branch templates:

   Group.branch_query_prompt_template:1   "...does this entry's entire information (aliases, description, purpose, culture, resources, events, relati..."
   Group.branch_update_prompt_template:18  '{"path": "aliases.0", "value": "New Alias for Group"},'  (a worked update-example line)
   StoryEvents.branch_query_prompt_template:1 "...any event's name, forma..."

### 1.1 Verdict — is the alias contract clear/unambiguous?

NO, on all three axes asked:

(a) genuine alias vs distinct entity's name — NOT addressed. The closest instruction is the
   per-relationship placeholder ("nicknames ... for the related character in the context of
   this specific relationship") — it never says an alias must refer back to the SAME entity,
   must not be another existing entity's key, or must not be an entity's formal name used as
   a handle. "The Handler"/"Second Runner" style handles are indistinguishable, to the
   model, from a nickname of the related character.
(b) may an alias equal another existing node's key — NOT addressed. Nowhere in schema,
   placeholder, example, or any of the 34 templates is there a canonical-key constraint
   ("alias must not collide with a distinct entry's key"). The only collision logic in the
   whole extension is the add_new name filter (_filter_new_entry_names) which runs on ENTRY
   KEYS, not on alias values.
(c) where aliases live — PARTIALLY addressed, inconsistently. The schema declares aliases as
   per-node fields (CharacterGroupStatus.aliases, Group.aliases, StoryEvent.aliases) AND as a
   per-relationship field (CharacterRelationship.aliases) — i.e. both a per-node field and a
   nested per-relationship field exist, and the parse side (_collect_entry_aliases) itself
   walks both shapes. The model is never told which shape to use for a given observation,
   which is one axis of the poisoning (a name attached to the wrong node's subtree).

### 1.2 Parse side — agents/data_summarizer/parsing.py

`_collect_entry_aliases` (parsing.py:71-92): walks a nested entry recursively (depth<=5,
list-cap 200) collecting every string in any `aliases` list at ANY level — top-level entry
aliases, per-group-status aliases, per-relationship aliases. Pure collection; NO validation:

    def _collect_entry_aliases(entry, out=None, depth=0):
        ...
        if isinstance(entry, dict):
            for k, v in entry.items():
                if k == "aliases" and isinstance(v, list):
                    out.extend(a for a in v if isinstance(a, str))   # verbatim, unchecked
                else:
                    _collect_entry_aliases(v, out, depth + 1)

Where does alias data ENTER the store? Via the generic update path — branch updates
(`_apply_branch_updates`, updates.py:417-473) and field updates (`_update_field` ->
`_generate_field_update`, updates.py:679-744 / 475-677). Neither path validates alias values:

- `_apply_branch_updates` (updates.py:432-448): parses (path, value) pairs, canonicalizes the
  PATH only (`_resolve_path_keys`, parsing.py:117-180 — exact / dot-join / normalized /
  alias-key resolution), then `recursive_set(data, keyList, value)` with the value verbatim.
  The value side is subject ONLY to: shape/type coercion (coerce_container_types) and a list
  null-scrub (updates.py:453-463, shape-only: drops None/""/"null"/"none"). No referent
  check, no collision check against other entries' keys/aliases.
- `_generate_field_update` (updates.py:596-616): a list field (aliases IS `list[str]`, so this
  is the path alias updates take) is parsed via `_tolerant_json_loads` and returned as-is;
  fallback splits on commas (updates.py:616). Schema validation is `validate_data`
  (updates.py:646-657) — JSON-schema shape/type validation, which passes any string list —
  and on max-retries the value is ACCEPTED WITH WARNINGS (updates.py:655-657).

Answer to the parse-side question: NO. There is zero validation anywhere that an emitted
alias does not collide with (normalize-match) a distinct existing node's key. Alias arrays
are accepted verbatim into the node's subtree. (The only alias-aware check in the extension,
`_filter_new_entry_names` at parsing.py:277-279, runs exclusively on NEW-ENTRY KEY proposals
in the add_new/discovery flow — it never touches alias values, and it SKIPS (drops) the
novel key rather than retargeting it, which is the exact behavior that produced the split
node: "Second Runner" vs "The_Second_Runner" both survived because... see Task 3.)

### 1.3 Render side — poisoned aliases fed back?

Yes — feedback loop confirmed. Three independent render paths feed stored alias arrays
back into model prompts each turn:

1. WHOLE-MAP RESTATEMENT (all update prompts). `_context_restatement` (prompts.py:92-142)
   renders `formatted_data.mark_field(branch_name)` — the ENTIRE rendered subject map
   (characters incl. their alias arrays) — and appends it to EVERY per-entry prompt
   (updates.py:101 gate check, :291 branch query, :352/:397 branch update, :552-554
   field update). So a poisoned alias array (Juno.aliases ~ ["Second Runner","Vell"]) is
   re-shown to the model on every call to every branch. In auto mode above the 10k-char
   threshold (prompts.py:65) it degrades to a compact sibling-roster of KEYS only
   (prompts.py:133-139) — which keeps foreign keys visible near the boundary.
2. RAG entity matching. `rag/structured_rag/message_chunker.py:199-213,365-368:
   `_create_name_alias_patterns` merges each entity's `aliases` into its regex match
   patterns — a poisoned alias makes OTHER being's mentions resolve to the wrong entity in
   retrieval (cross-entity retrieval bleed).
3. UPDATE-PATH RESOLUTION. `_resolve_path_keys`/`_resolve_dict_key` (parsing.py:95-114)
   resolve an emitted key via other entries' alias arrays — so once aliases are poisoned,
   even path canonicalization can retarget a write AT ANOTHER ENTITY'S ALIAS onto the
   poisoned node (updates to Vell landing on Juno's subtree when Juno.aliases contains
   "Vell"). The parse side's alias awareness, meant to be a kindness, becomes a
   propagation channel after poisoning.

Render-side answer: YES, the poisoned alias array is rendered back — repeatedly (map
restatement on every summarizer call) and consumed by both RAG matching and path
canonicalization. The loop: model emits foreign name as alias -> stored verbatim ->
restated into future prompts AND used to resolve keys -> model sees/updates the wrong
attribution -> repeats.
## Task 2 — BRANCH QUERY MECHANICS (gate -> edit)

### 2.1 The ~5 LLM call sites (all funnel through `_create_update_prompt`, prompts.py:354)

Every summarizer LLM call is built by `_create_update_prompt` (prompts.py:354-521). The five
user-recalled sites map to these call sites:

| site | call site | file:line | template key |
|---|---|---|---|
| gate check | `_perform_gate_check` -> `_create_update_prompt` | updates.py:83-90 | `gate_check_prompt_template` |
| branch query (does it need edits?) | `_perform_branch_query` -> `_create_update_prompt` | updates.py:263-270 | `branch_query_prompt_template` |
| branch update (list of field edits) | `_perform_branch_query` -> `_create_update_prompt` | updates.py:341-348 | `branch_update_prompt_template` |
| branch update, update-only (skip_query) | `_branch_update_only` -> `_create_update_prompt` | updates.py:385-392 | `branch_update_prompt_template` |
| full-branch dict replacement | `_perform_full_branch_update` -> `_generate_field_update` | updates.py:199-209, 540-549 | `update_prompt_template` |
| field-level single-field edit | `_update_field` -> `_generate_field_update` | updates.py:731-740, 540-549 | `update_prompt_template` / per-field |

### 2.2 What subject data each site injects (the KEY QUESTION)

`_create_update_prompt` has exactly ONE data-injection mechanism (prompts.py:382-397): it
`recursive_get`s a single value at the path `keys + [field_name]` and serializes it into the
`{value}` slot. If `field_name` is empty (the branch-level call sites above), `path_to_value`
is just `keys` and `current_value = recursive_get(data, keys)` = the WHOLE branch dict — BUT
that value is only emitted IF the template has a `{value}` placeholder. This is the deciding
mechanism, and the templates differ:

- **Field-level edit** (`_update_field`, a leaf `field_name` non-empty): `field_name` is
  appended to the path, so `{value}` = the target's CURRENT value for that exact field. The
  built-in default template (updates.py:717-726) is: `"is the field '{field_name}' for item
  '{item_name}' inaccurate or incomplete?  Current value: ``` {value} ``` ..."` =>
  **INLINED — the target's current full data for that field IS in the prompt.**
- **Branch-level call** (`field_name=""`, the branch_update / gate / full-update sites): no
  single field is pulled. Whether the branch's current data reaches the model depends purely
  on whether the branch template contains `{value}` — see 2.3.

### 2.3 Per edit site: INLINED vs THIN (settled from the template + the live dump)

Template placeholder audit (all 34 extracted templates, tests/_tmpl_extract/):

| site / template | `{value}` | `{schema_snippet}` | `{branch_list}` | verdict |
|---|---|---|---|---|
| Character.branch_update (per-character edit = the alias/relationship path) | ABSENT | present | ABSENT | **THIN** |
| Group.branch_update | ABSENT | present | ABSENT | **THIN** |
| Character.branch_query | ABSENT | ABSENT | ABSENT | **THIN** (query-only) |
| Group.branch_query | ABSENT | ABSENT | ABSENT | **THIN** (query-only) |
| StoryEvents / SceneState / GeneralInfo / Arc / Chapter update | present | present | ABSENT | **INLINED** |
| new_entry_query (all maps) | ABSENT | ABSENT | **present** | roster-only (names) |

**The alias/relationship edit path is THIN.** A character's alias/relationship rows are
updated through the per-entry `Character` branch action — `Character.triggers` =
`[{"always":[{"action":"query_branch_for_changes","skip_query":true}]}]` (schema) — i.e. the
`branch_update_prompt_template` with the pre-query skipped. That template
(`tests/_tmpl_extract/__Character__branch_update_prompt_template.txt`) contains `{{schema_snippet}}`
and `{{example_json}}` but **NO `{value}`** — it says:

    "Based on the latest exchange, review the current state of the entry below."
    ..."If any specific fields within the entry require updates (additions, modifications, or
    deletions), please provide a list of these changes. Each change should specify the 'path'
    to the field and the 'value' for the update."  ...  "Entry to review: '{{branch_name}}'"

The word "below" is unbacked: nothing below shows the entry's current alias array or its
existing relationship rows. The ONLY ground truth appended is `_context_restatement`
(prompts.py:92-142). In the live run that restatement is **degraded** (see Task 3) to a
keys-only sibling roster. => **Verdict: the model is shown a branch pointer + schema + a
keys-only sibling roster, and is forced to reconstruct the alias/relationship content from
scratch.** This is the "model NOT shown what it's about to overwrite" form of the defect —
NOT "shown the data but still emitted a foreign referent."

### 2.4 GATE -> EDIT data flow

`_execute_action` (core.py:243-368) runs the action ladder per branch, in order:
`ADD_NEW` (core.py:282) -> `PERFORM_GATE_CHECK` (core.py:300-311) -> `PERFORM_UPDATE`
(core.py:313-324) -> `QUERY_BRANCH_FOR_CHANGES` (core.py:326-354) -> `SELECT_ENTRIES_TO_UPDATE`
(core.py:356-366). The GATE decision is `_perform_gate_check` (updates.py:67-179): a yes/no
LLM call on `gate_check_prompt_template`, fail-open (defaults to process / True on a
non-verdict, updates.py:178-179).

**The gate's evidence is NOT passed to the edit step — the edit step re-renders the subject
independently.** Each site rebuilds its prompt from scratch via `_create_update_prompt` with
the same `keys`/`formatted_data`/`schema_class` and a fresh `_context_restatement`
(updates.py:101 gate, :291 query, :352/:397 update, :552 field). The gate's triggering
evidence (the exchange) is re-injected at the edit site as `{{exchange}}`/`{{user_input}}`/
`{{output}}`/`{{scene_recap}}` (prompts.py:478-482), NOT forwarded from the gate. So the edit
step sees: schema + example + (degraded) restated roster + re-rendered exchange — and, for the
THIN branch path, NO current data of the field about to be overwritten.

## Synthesis — what the pre-mutation referent-resolution gate must be

The gate must be BOTH, and the two halves attack different halves of the defect; neither
alone closes it:

1. A PROMPT-CONSTRUCTION change (primary, and the rule-#278-compliant one).
   - Inline the target's CURRENT full data at the edit boundary: give the THIN branch_update
     path the same ground-truth the INLINED field-level path already gets — the entry's
     existing alias array + existing relationship rows (a `{value}`-style slot populated
     from `recursive_get(data, keys)`), so the model is shown what it is about to overwrite.
     This converts Task 2.3's THIN verdict to INLINED at the exact site where alias/
     relationship rows are written. It also restores a preserve-vs-replace signal the
     degraded restatement (Task 3, quote 3) destroyed.
   - Add a CANONICAL-KEY CONSTRAINT to that same prompt: every emitted referent (alias or
     relationship partner) MUST resolve to a key in the provided sibling roster / must equal
     a canonical key already in the target's own array; foreign handles observed only in
     prose are not valid referents. This is what the schema + all 34 templates currently
     lack (Task 1.1 verdict b).
   => Fixes the root cause at the source: emitted strings validate on first generation.

2. A PARSE-TIME validation (secondary — a belt, not the fix).
    - Reject/retarget any alias or relationship-partner value that collides with a DISTINCT
      existing node's key. Build the collision set from `_normalize_entry_name` + the
      containment logic already at parsing.py:267-276; today that machinery runs ONLY over
      new-entry KEY proposals (`_filter_new_entry_names`) and only to REJECT — it never runs
      over alias or relationship values (Task 1.2). Extending it to (a) alias arrays and
      (b) relationship partners, and changing the action from REJECT to RETARGET-onto-the-
      matched-existing-node (when the emit is an alias/handle) or DROP (when it is a novel
      key), is what actually stops a foreign referent being stored. Plain normalize-collision
      is not sufficient: 'Second Runner' vs 'The_Second_Runner' normalize to DISTINCT
      strings ('secondrunner'/'thesecondrunner'), so the split node needs the CONTAINMENT
      match ('secondrunner' in 'thesecondrunner') to catch it — a check that today fires
      only to reject a novel proposal, never to retarget.

Why both: rule #278 (never patch mismatched LLM output with a downstream workaround) makes
the PARSE-TIME gate unacceptable as the sole fix — it is, by definition, a downstream
workaround on first-generation output, and it cannot teach the model the contract. But the
PROMPT-CONSTRUCTION change alone is probabilistic: a small-active model given the ground
truth plus a constraint can still emit a colliding referent on a given turn, and with no
parse-time check that emit is stored verbatim and re-rendered (Task 1.3 feedback loop).
The prompt change makes first-generation correctness the NORM and shrinks the collision
rate; the parse-time check makes the residual a non-event (reject/retarget) instead of
permanent store corruption. The map shows the defect is BOTH 'model not shown what it's
about to overwrite' (fixed by inlining) AND 'no canonical-key contract + no collision
scrub' (fixed by the constraint + the parse-time retarget).
