DSS ⇄ Smart-Memory
feature matrix & performance model

Line-for-line capability comparison between Smart-Memory (SillyTavern extension, v1.8.1 — reference implementation at extensions/dayna_ss/.ref/Smart-Memory) and the DAYNA Story Summarizer (TGWUI extension, v0.2.x). Every feature is classified as should have, nice to have, or doesn’t need — with architectural rationale — followed by a parameterized prefill/decode cost model comparing both systems’ per-turn latency.

01

Verdict summary

Should have (4)

  • Epistemic knowledge maps — who knows / suspects / falsely-believes / is-unaware-of / conceals what (SM’s Perspectives & Secrets)
  • Story-so-far canon synopsis — one distilled narrative paragraph-set, distinct from live scene state
  • Continuity contradiction check — cheap gate-time probe that flags updates contradicting established facts
  • Cross-session fact carry-forward — seed a fresh chat’s world model from a prior session’s resolved state

Nice to have (11)

  • Away recap modal (“previously on…”, SM: ≥4 h gap)
  • Embedding-similarity guard on ADD_NEW discovery (SM: cosine + Jaccard)
  • Update audit trail / supersession view (SM: retired pool)
  • Entity merge/delete tooling + graph visualization canvas
  • Live token telemetry of the rendered context
  • Read-only mode with commit/discard checkpoints
  • Ledger-style starter field packs (schema examples)
  • Generation-lifecycle hooks (swipe-abort, delete/edit) from SM’s validated list
  • Hardware-tiered output-format fallback (tagged text if JSON compliance fails on small models)
  • MCP server wrapper over the import-clean core
  • Slash commands for quick queries

Doesn’t need (7)

  • Regenerated profile snapshots (character_state / relationship_matrix) — DSS always renders live state
  • Confidence-decay bookkeeping — importance system + whole-branch replacement make stale confidence meaningless
  • ST macro surface ({{smartMemory}}) — different host architecture
  • Unified-injection toggle — DSS owns prompt assembly outright
  • Migration framework — until schema/user-data versioning actually drifts
  • Group-chat hot-swapping — name1/name2 binding is core to DSS identity guards
  • Duplicate session-bullet tier — events subject + chunked message index already cover recency

Covered differently (9)

Same job, opposite mechanism — see §03:

  • Rolling short-term summary ⇄ current_scene + rolling summaries
  • Multi-slot depth injection ⇄ single assembled _context_order block + placement matrix
  • Hybrid vector search ⇄ full-state render + graph traversal
  • Model test harness ⇄ soak harness

How to read the matrix

ColumnMeaning
Smart-MemoryWhat SM ships today (v1.8.1), with the implementing module.
DSS status● has  ◖ partial  ○ lacks — plus how DSS handles the concern today.
Verdictshould have high-value adoption target · nice to have worthwhile, lower priority · doesn’t need actively counterproductive or redundant under DSS’s design · covered differently same outcome, different mechanism — do not port.

Rationale consistently weighs DSS’s three structural differences: (1) schema-driven editable world model vs fixed JS behavior; (2) whole-branch validated replacement vs accumulating tagged text lines; (3) every-turn summarization cadence vs threshold-triggered passes.

B · Knowledge organization
Epistemic perspectives & secretsepistemic.js Five-tag who-knows-what map per character: [knows] [suspects] [believes] (falsely) [unaware] [hiding](from target); deception maintenance moves entries between tags as the story confirms them; injected per responding character. ○ none. Character entries hold relationship/status facts but no theory-of-mind layer; retrieval shows everyone the same omniscient truth. should have The single highest-value gap. Dramatic irony, mysteries, secrets and misdirection are impossible when the narrator is omniscient-by-default. Adopted shape (full rationale in the P0 roadmap entry): a normalized secrets map subject where each row is one perspective (stance / owner / target? / about? / status / importance) — one fact = one row; POV injection filters rows by owner ∈ scene cast; a reveal flips status on a single small branch under mark_field. Relationships may reference secret names like relevant_events for render-time joins onto relationship cards, but authoritative linkage lives in the row (owner/target/about) so non-dyadic secrets ("she knows about the passage") stay first-class; group-level rows carry institutional semantics (shared secrets, collective stances, rumor penetration). Why DSS’s generalism wins here: SM models P&S as epistemic tags on per-character isolated stores — asymmetry by storage layout, so a truth change must patch every store mentioning it (the drift source). DSS keeps one shared world model with vantage as a query parameter: adding a POV character costs zero migration, and epistemic state is ordinary typed schema fields — gate-check/update generality applies free, including future reliability fixes propagating automatically. Structurally this converges on SM’s bipartite person↔secret topology; the difference is declarative schema vs hardcoded retrofit.

Ship a “ledger field pack” example schema (six character card fields + object/place classes) so users get SM-grade physical-state tracking by uncommenting rather than authoring.

04

Performance model

Standalone calculator: docs/performance_estimator.py. It models per-turn wall-clock added by each memory stack as:

turn_cost = main_prefill(injected_tokens / prefill_tps)
          + main_decode(reply_out / decode_tps)
          + SUM(background_calls: call_input/(prefill_tps·(1−prefix_hit)) + call_out/decode_tps)
SM calls are averaged over their extraction cadence (default every 3 msgs); DSS calls recur every turn.
Anchors. DSS balanced measured ~46 calls / 230 s serially over a clean 2-turn smoke (≈23 calls/turn — the model predicts 21.7). Parallel workers cut it to 128 s (≈1.8×). SM publishes no benchmarks; its docs describe “several seconds per Ollama call.” DSS injected-token components (general_info 550, current_scene 260, arcs 320, characters 6×520, events 420…) derive from the shipped sceneagg schema’s rendered sizes; SM figures from its advertised budgets (steady-state ≈3750–4200 tok, cap 5750).

Reading 1 — prefill dominates DSS

DSS is ~128:1 prompt:completion. Its cost scales almost purely with prefill throughput. On cloud-fast DSS-balanced (64.7 s) sits ~4× above SM-default-b (16.3 s), and that ratio holds across profiles (2.9–4.0×) because both stacks scale together — what changes is absolute pain: at laptop / dense-70B speeds both add 2–11 minutes per turn, making fast-prefill MoE hardware DSS’s natural habitat.

Reading 2 — SM buys latency with amnesia

SM’s 24–43 s/turn buys selective injection of ~4k tokens. DSS’s 98–138 s buys the entire validated world model rendered every turn plus a directed instruction block. The comparison isn’t “same feature, slower” — the injected artifact is categorically richer.

Reading 3 — the levers differ

DSS tuning = fewer/larger engine calls: skip_query halves per-entry cost (light = −29%), selection whitelists, worker parallelism overlaps decode. SM tuning = cadence and caps. Both systems’ worst case (“everything on”) is within 3× of their default — neither falls off a cliff.

Suggested adoption roadmap

PhaseItemRationale & shape
P0 Epistemics: normalized secrets subject Adopted design (supersedes the five-tag-lists sketch): one secrets map subject where each row IS one perspective — {summary, stance: knows|suspects|believes_falsely|unaware|hiding, owner, target?, about?, status: intact|suspected|exposed, importance}. One logical fact = one row; Paul’s side is a second row (stance: unaware) or nothing, never duplicated prose. A reveal flips status/stance on a single small branch under mark_field — surgical deception maintenance. POV injection = group rows by stance over owner ∈ current_scene.now.who — no per-character tag lists to maintain. Relationships/characters may reference secret names like relevant_events for render-time joins onto relationship cards, but authoritative linkage lives in the row (owner/target/about) so non-dyadic secrets stay first-class. Group-level rows cover institutional semantics (shared secrets, collective stances, rumor penetration). Plumbing largely exists: reference-list fields are the relevant_events idiom, _build_from_schema can emit typed edges from them, secret nodes can enter entity_graph.json without touching scored truth-edges, ADD_NEW discovers significant secrets via the ordinary path, and the universal importance rubric tiers rendering. Guardrails: significance threshold in discovery prompts (only revelation-relevant facts become rows — trivial awareness stays unstructured; long soaks would otherwise mint hundreds of stubs against the 120-entry caps); alias-table rename discipline for references. Phase 2 (optional): derived person↔secret edges for visualization/vantage queries — structurally converges on SM’s bipartite shape but falls out of declarative schema with engine generality applied free, not their hardcoded retrofit. Vocabulary from the NWM paper: focalization, event-vs-reveal order, promise/payoff. Placement decisions recorded along the way: per-relationship-row storage rejected (topical-not-dyadic problem, dual-sided duplication, fattens characters.json payloads on a prefill-bound workload); faction untouched (orthogonal affect axis feeding edge scoring). Directly answers the omniscient-narrator limitation.
P0 Canon synopsis at chapter archival Derived subject appended at chapter close: ~300-token narrative digest. Renderer swaps closed-arc full profiles for synopsis references. Caps the linear token growth of long runs — the one place DSS’s render-everything philosophy needs a pressure valve.
P1 Gate-time continuity probe Optional engine step diffing proposed vs current branch; flags contradictions with immutable-ish facts; schema-flag gated. Protects whole-branch replacement from silent hallucinated overwrites.
P1 Resolved-state export / sequel import Export final subject JSON + arcs as a portable pack; import as a seeded initial_world_cache variant. Gets cross-session longevity without the LT-pool machinery.
P2 Discovery similarity guard Reuse the resident mpnet index to score ADD_NEW candidates against existing entries (cosine >~0.85 → merge instead of create). Prevents long-soak entity sprawl.
P2 Ledger field pack + active-arc pinning Example schema declaring location/injuries/outfit/mood/goal/items character fields; _active/_resolved thread flags with render-first ordering. Pure schema/renderer work, zero engine changes.
P2 Dry-run turns + context telemetry over SSE Approve/discard per-turn updates while tuning schemas; emit per-block token counts on the existing event stream. Operational safety, borrowed straight from SM’s best UX ideas.
P2 Dyad canonicalization pass Objective-layer hygiene without storage migration: at build time, reconcile mirrored per-entity relationship rows into ONE canonical edge per dyad (higher-importance side wins, deterministic tie-break; union events/scenes; mark bidirectional; log discarded-side conflicts to activity log). Closes the one place subjective drift leaks into the objective graph today — _add_typed_relationship currently appends both sides verbatim (entity_graph.py:484). Zero new LLM calls; keeps per-entity authoring grain.
P3 Away recap, entity timeline view, graph canvas Polish tier. Recap from rolling summaries; timeline from recorded old_values; canvas served off the SSE host reading entity_graph.json.
P3 MCP server wrapper Expose the import-clean core as an MCP server (MemoryMesh is prior art). The distribution mechanism for “usable by others, truly extensible” — and structurally unavailable to SM without a rewrite.
P2 Generation-lifecycle hooks + small-model compliance sweep Copy SM’s validated event list (swipe-abort, delete/edit) instead of re-deriving it; run tests/live_benchmark.py across the small-model tier (V100: Qwen2.5-1.5B, Llama-3.2-1B/3B) to decide whether a tagged-text fallback profile is warranted.
